# 首帧失败跟进 — 2026-11-05

## 结论

确认并修复了一个能够稳定造成同类首帧失败的超时设计缺陷：原来的 **20 秒计时从网络解析前开始**，把冷启动、共享解析器等待、proof 初始化、媒体解析、解码和初次追帧全部算在一起。底层解析器本来允许 90 秒操作预算，部分 HTML/脚本请求允许 60 秒，因此合法的较慢初始化会被视频层抢先取消。

在受控复现中，失败发生时 **解码器还没有启动**；因此这组复现不是 FFmpeg 已运行后随机不输出画面。

旧的那一次 `first_frame_failed` 只保留了总结果，没有阶段和取消原因，无法唯一还原当时具体哪一次上游请求慢。此次实验明确证明这个设计缺陷可产生相同症状，并验证修复消除了该类误超时；没有把故障注入数据当作自然网络波动。

## 实现

- 解析独立限制为 **90 秒**，包含冷初始化和共享解析器等待，与原生 resolver 的操作预算一致。
- 解析结束后启动 **30 秒首帧预算**，覆盖打开解码器和全部初次追帧；重试不能重置该预算，显示首帧后停止计时。
- 后续播放停顿仍使用原有 10 秒限制。显式停止、取消和替换仍立即取消工作并回收资源。
- 保留上游固定错误分类及安全元数据；缺少上游阶段时使用 `video_resolution` / `video_first_frame` / `video_playback`。新一次开始、成功显示、停止均清除旧错误元数据。
- 原生视频诊断保存这些安全阶段。实时测试的调用者截止时间也与生产阶段预算对齐，避免测试自身先取消正常启动。

主要实现为 `internal/player/video.go`、`internal/player/failure_details.go`、`video_controller.go`；新增回归和实时分阶段探针。
